# The splitter and document ingestion: what could move to the browser

Status: research (2026-10-11). Nothing here is built or decided. The question: could any of the splitter's work, and more broadly document ingestion, be offloaded to client-side JavaScript, thumbnail generation for instance? General for any association; samples are made-up. It answers against [pdf-splitter.md](pdf-splitter.md) (section 3, the thumbnail pipeline, and decisions 9.3 and 9.3a), [instance-limits.md](instance-limits.md), [console/screens/split.md](console/screens/split.md), and the code in `src/jason/tasks/split_thumbs.py`, `split_session.py`, `split_suggest.py`, `split_flags.py` and `ui/src/views/splitThumbs.ts`, `splitWindow.ts`, `splitFacts.ts`.

**The short answer.** Yes for four things, no for the rest, and the server stays the authority for everything that is applied.

1. **Yes, now:** hash the file before it is sent (SubtleCrypto SHA-256) so the server can say "already held" and skip the upload; read file-level facts (size, `%PDF` header, a cheap page-count probe) before sending; and send the file in pieces. All of it is a convenience: the server re-hashes, and the answer it keeps is its own.
2. **Yes, but only as a second path:** a browser renderer (pdf.js) for thumbnails, for a deployment where the server has no renderer, is far from the file, or serves many communities. Measured below, pdf.js drew the made-up pages correctly in every codec but one it had to be configured for, at speeds the server beats by two to five times per page at grid sizes and the browser beats by parallelism. It is not faster than the server on the same machine, and it is no cheaper for the person on a phone.
3. **No:** measuring the facts the server trusts (blank, sideways, near-duplicate, the page-number run) in the browser and sending them as the facts. Two renderers disagree by a measurable margin (below), and a client is untrusted.
4. **No:** cutting the PDF in the browser for apply. The server cuts from its own copy, and a cut made by a client would be a file nobody checked. The browser may cut a range *for upload* when the file is too large to send whole, but the server then holds a partial source and must say so.
5. **Not yet:** OCR in the browser. Unmeasured here (needs language data; section 5).

## 0. What the splitter does today, and where the cost is

Read from the code, not assumed.

| Step | Where | Cost shape | Source |
|---|---|---|---|
| Upload | one JSON request, the file as base64 (a third larger), bounded by `upload.max_bytes` (default 100 MB) | the whole file in the browser as a string, then in the server's memory | `open_session`, the `base64` branch in `src/jason/tasks/split_session.py` |
| Copy and hash | the server copies the bytes once into `<data>/split/sources/<sha[:2]>/<sha>.pdf` and hashes them | one pass | `sha256_of`, the copy step in `split_session.py` |
| Facts | one light pass: text layer, images, blank, size, label, `turn`, an LQIP, `phash` | sequential over the file, cached by hash in `<data>/split/facts/` | `scan`, `ensure_facts` |
| Pictures | `render_page(path, page, size)`: pypdfium2 if importable, else PyMuPDF; opened per call; WebP; hash-addressed cache with an LRU bound | one render per page and size, shared by every viewer | `src/jason/tasks/split_thumbs.py` |
| Display | `splitThumbs.ts` loads plain images by distance from the view, six at once, aborting on scroll, with a decoded-picture budget (150 tiny, 60 small, 3 large; half on a small device) | memory bound by pictures, not by the file | `ui/src/views/splitThumbs.ts` |
| Cut | `record_upload.cut_pages` with `pypdf`, deterministic, from the server's copy | at apply only | pdf-splitter.md 6.1, 9.4 |

Two facts from that table frame everything. The browser today never holds the PDF in a form it can parse, only a base64 string while uploading. And the server's copy, taken once and addressed by hash, is what every picture and every cut reads, "so a picture and a cut read bytes that cannot change under them" (9.4). A client-side path must not weaken that.

## 1. What was measured, and how

All inputs are made up and generated by `scripts/client_pdf_make.py` into a scratch folder outside the repository (no real scan, not any archive). They are one-image-per-page PDFs: 1-bit CCITT Group 4 at 200 dpi (4.6 MB for 100 pages), colour JPEG (DCT) q70 at 200 dpi (44 MB), 8-bit Flate grey at 150 dpi (9.5 MB), colour JPEG 2000 at 150 dpi (33 MB), a 2,000-page CCITT file (93 MB), a 500-page vector-text file (5.7 MB), and a 105 MB random file for hashing.

Browser: Chromium 153 headless (Playwright 1.63.0 with the Chromium already cached; no browser was downloaded), pdf.js 5.4.149 (Apache-2.0) from `npm`, served from the same local origin, no CDN. Machine: 32 logical cores, Windows 11, local loopback. Server: `scripts/client_pdf_server_bench.py`, the same functions `split_thumbs` uses, PyMuPDF 1.28.2 (pypdfium2 is not installed in this checkout's environment, so it was not measured), Pillow 12.3 WebP. The drivers are `scripts/client_pdf_bench.mjs` with `scripts/client_pdf_bench.html`. Median of 30 pages (5 pages spread across the 2,000-page file); a page is "render" plus a WebP encode of the canvas.

**Caveats that matter.** One machine, desktop-class, an empty system: a phone is not measured, and a phone will be several times slower (unverified). pdf.js paints on the main thread in animation-frame steps, so a fast page costs at least one frame (about 16.7 ms): the browser's 14 to 31 ms medians below are largely that quantum, not decoding. The server figures here are higher than the caller's recorded server numbers (about 2.1, 3.8 and 47.6 ms per page for 96, 200 and 800 px WebP; I could not find that record in the repository, so it is unverified): these were measured with the files being written on the same disk and an open per call, so read the *ratio* between the two, not either number.

### Per page, median ms (render + WebP encode), 30 pages

| Source | 96 px browser | 96 px server | 200 px browser | 200 px server | 800 px browser | 800 px server |
|---|---|---|---|---|---|---|
| CCITT G4, 1-bit | 31.8 | 6.8 | 33.4 | 9.7 | 50.2 | 59.8 |
| JPEG (DCT) colour | 17.0 | 5.9 | 33.0 | 8.8 | 49.6 | 62.3 |
| Flate grey | 15.7 | 6.6 | 17.0 | 9.5 | 49.8 | 58.1 |
| JPEG 2000 colour | 79.0 | 84.2 | 80.9 | 85.1 | 107.3 | 138.1 |
| Vector text (500 pages) | 16.2 | 9.7 | 16.6 | 12.6 | 49.4 | 60.0 |

Reading it: at the sizes the grid uses (96 and 200 px) the server is two to five times faster per page; at 800 px the encode dominates and the two are level; JPEG 2000 is slow on both (about 80 ms a page), so it is the codec to ration. The browser's advantage is **parallelism it does not pay for**: six pages at once drew 57 to 81 pages a second at 200 px (CCITT, DCT, Flate) and 261 for vector text, because pdf.js decodes in its own worker; a single server process draws about 100 pages a second at 200 px, and the server's workers are shared by every viewer of every community. JPEG 2000 in the browser managed 12.8 pages a second.

### Opening, the page-count ceiling, memory

| Measure | Result |
|---|---|
| Fetch + open, 4.6 MB to 44 MB files | 43 to 49 ms to open (the file was already in memory, fetch 18 to 76 ms on loopback) |
| 93 MB, 2,000 pages, whole file in memory | opens in 60 ms; pages 1, 500, 1000, 1500, 2000 draw at the same 31 ms; fetch 206 ms on loopback |
| Same file with HTTP range requests (`disableAutoFetch`) | opens in 758 ms and holds about 100 MB of JavaScript heap afterwards (the page tree and xref), against 3 MB for the whole-file path, which keeps the bytes outside the heap; draws at the same speed. Range mode is not a memory saving for a 2,000-page file |
| Total browser working set over the whole run | peak 259 MB across all of the above (every browser process, the 105 MB hash file and the 93 MB PDF included); not a per-file figure |
| Longest main-thread task | 81 ms on pages that decode large images (pdf.js, not the page's own code); the rest under the 50 ms long-task threshold |
| SHA-256, 105 MB | SubtleCrypto: 71 ms (about 1.5 GB/s); Python `hashlib` over the same file 83 ms; digests identical |
| Cut 11 of 2,000 pages | pdf-lib 1.17.1 (Node): 864 ms to load the 93 MB file, 12 ms to copy and save; pypdf (server): 137 ms in total. pdf-lib reads the whole file; pypdf reads lazily |

Reading it: the memory ceiling is not hit by anything here, because the machine is large. The risk is the phone: the whole file is an `ArrayBuffer` for SubtleCrypto (which has no incremental interface: digesting a file means holding it) and for pdf.js's `data` mode. A 400 MB scan on a 2 GB phone is the case this section cannot test (unverified), and the design in pdf-splitter.md 3.4 (never give the browser the file) exists for it.

### Two renderers disagree

Page 1 of each file, drawn by pdf.js and by PyMuPDF at the same size, as 8-bit grey: mean absolute difference 4.2 to 7.3 levels of 255; the share of pixels below 200 (a stand-in for "ink") differed by up to 18 percent of itself (0.1255 server against 0.1370 browser for the CCITT page at 200 px; 0.1173 against 0.1383 for DCT). They agree on content and disagree on anti-aliasing and scaling. A blank-page threshold or a "marked" threshold measured on one renderer's picture and applied to the other's would flip some pages. The client-side ink test itself is cheap (0.05 to 1.5 ms a page at 200 to 800 px for the pixel loop).

### What did not work until configured

pdf.js 5 loads its JPEG 2000, colour-management, character maps and standard fonts from files it fetches (`wasmUrl`, `cMapUrl`, `standardFontDataUrl`). **Without `wasmUrl` the JPEG 2000 pages drew as white pages with no error**: a first run, with those options unset, measured 15 ms a page and zero ink; with them set, about 80 ms a page and the same ink as the server. A silent blank is the worst failure for a splitter (it looks like a blank separator). Any client path must therefore ship and self-host those assets (the `wasm` folder is 820 KB, `cmaps` 1.4 MB, `standard_fonts` 804 KB in the 5.4.149 package) and test that a known JPEG 2000 page is not blank at start.

### Not measured

- **JBIG2.** No encoder is installed here (no `jbig2enc`, no tool that writes it; Pillow and PyMuPDF do not). pdf.js decodes JBIG2 in JavaScript, not WebAssembly (the package ships no JBIG2 wasm; the worker is 1,016 KB minified, 287 KB gzipped). Whether it matches PyMuPDF on real JBIG2 scans, and how fast, is **unverified**. Both CCITT G4 and JPEG 2000 were generated and drew correctly.
- **OCR** (tesseract.js, ONNX/RapidOCR in WebAssembly), **pdfium in WebAssembly** (EmbedPDF), **mupdf.js**, **CanvasKit**: not installed or run; sections 2 to 5 give what the projects say about themselves and mark it.
- Phones, Safari, Firefox; files over 100 MB in a tab; a long soak.

## 2. Decision table

| Task | Client, server, or both | Why |
|---|---|---|
| SHA-256 of the file, before upload | **both**: client computes, server recomputes and wins | 71 ms for 105 MB; lets the client skip an upload the server already holds; a client's hash is a hint, never a key to anything (the server's copy is keyed by its own hash) |
| File-level preflight: size against `upload.max_bytes`, `%PDF` header, encrypted flag | **both** | saves a doomed upload; the server repeats every check and its words win |
| Upload: chunked, resumable, skip by hash | **both**; server stores and assembles | removes the base64 inflation and the one-request ceiling; needs a new route (section 6) |
| Page count and page sizes before upload | **client, advisory** | one cheap read; the server counts again against `split.max_pages` |
| Thumbnails and page pictures, default | **server** | 2 to 5 times faster per page at grid sizes on the same machine; one render shared by every viewer and cached by hash; access rules and confidential masking in one place; the browser never holds the PDF (pdf-splitter.md 3.1) |
| Thumbnails, where the server has no renderer, or the server is remote or shared | **client (pdf.js), optional** | 57 to 81 pages a second at 200 px with no server CPU; costs the file in the browser (section 3) |
| Compare and zoom pane at high magnification | **client, lazy, one page** (pdf-splitter.md decision 1 stands) | vector sharpness; one-page PDF from the server, not the whole file |
| Blank, marked, sideways, `turn`, near-duplicate, page-number run, DPI, colour, codec | **server** | they are the facts suggestions and flags are built from; the server measures from the PDF's text layer and images, not from a picture; a client may display a pixel-derived hint, labelled as one, that no suggestion or flag reads |
| Page-number run from the text layer | **server** (client could read it, no reason to) | the server's `PageFact.label` already comes from the text layer; a second source is a second answer |
| Near-duplicate image hashing | **server** (`PageFact.phash`) | a browser mean-hash of a differently anti-aliased picture would not match the server's; the existing hash is on the server's own drawing |
| OCR | **server** (local lane) by default; browser **no go for now** | engines and language data are large; quality on archival scans is unmeasured; the server's lane already does it (pdf-splitter.md 9.5) |
| Cutting the PDF for apply | **server** | one copy, deterministic bytes, the collision and hash rules; a client-cut file is unverified input |
| Cutting a page range for upload of a file too large to send | **client, optional, with the server told** | saves bandwidth; the server then holds a partial source and says so |
| Draft marks, undo, windowing, the picture loader | **client** (already) | no PDF involved |

## 3. Thumbnail and page rendering

### Engines

| Engine | What it is | License | Notes (a claim from the project's own page is marked) |
|---|---|---|---|
| **pdf.js** (`pdfjs-dist`) | Mozilla's JavaScript renderer, worker plus main-thread canvas | Apache-2.0 (the package's `LICENSE`; measured above) | Measured: 4 codecs drew; 1,016 KB worker (287 KB gzipped) plus a 388 KB main script (111 KB gzipped); JPEG 2000 and colour-management in 350 KB of wasm; cmaps and fonts as files; JBIG2 in JavaScript. Cannot render in an `OffscreenCanvas` worker without extra work (unverified for 5.4; the library paints on the thread that calls `render`) |
| **pdfium compiled to WebAssembly** (EmbedPDF's runtime is a PDFium fork, and its repository is Apache-2.0 apart from a separate server under a source-available licence; the repository's own page says v3 is "not yet recommended for production use") | the engine Chrome uses | PDFium is BSD/Apache; the wrappers vary | Same engine as `pypdfium2`, the server's preferred renderer, so a client and a server agree most closely. Size, headless thumbnail use and speed: **unverified, not run here** |
| **mupdf.js** | MuPDF in WebAssembly, paints to canvas in a browser | **AGPL-3.0 or a commercial licence from Artifex**, covering the JavaScript and the wasm (the repository's page; pricing by contact) | AGPL in a bundle shipped to every browser makes the association's whole console subject to AGPL's source-offer terms for a network service (a legal reading: counsel, not this document). ### What the browser cannot do, or does with a risk

- **Codecs.** pdf.js drew CCITT G4, DCT, Flate and (with assets) JPEG 2000 here. JBIG2 is in JavaScript and untested here; PyMuPDF and pypdfium2 both handle it in C (their common use; not re-measured). A scanned archive is where JBIG2 and CCITT live, and the cost of a miss is a wrong page or a blank page.
- **Silent failure.** Without its wasm files pdf.js drew JPEG 2000 as white, with no error. The grid's "blank" glyph would read it as a blank page.
- **Memory.** pdf.js holds the whole file (as one buffer, or as its page tree under range requests: 100 MB of heap for the 2,000-page file). A 2,000-page, 400 MB scan on a 2 GB phone is the case that kills a tab (unverified).
- **Main-thread painting.** Page decode is in a worker; the paint of a large image is not. One 81 ms long task appeared. Jank under a fast scroll needs a render queue with a limit (the loader's six-at-once is the right shape).
- **`OffscreenCanvas`, Web Workers, `createImageBitmap`, WebAssembly, `crypto.subtle`**: all present in this Chromium. `crypto.subtle` needs a secure context (HTTPS or `localhost`); jason-web on a LAN address over plain HTTP has no SubtleCrypto (a known browser rule; confirm in the target browsers).
- **Cold start.** First open pays the worker and script load (about 1.4 MB over the wire gzipped before any page); measured first-page draws were 14 to 122 ms against a warm 14 to 80 ms.

### Correctness: two renderers

A picture from the browser is not the picture the server's facts were measured on. Differences are small (4 to 7 grey levels) but real, and they matter for any threshold. So: **a client picture is a display, never an input.** The server's facts, flags, suggestions and `phash` are measured on the server's drawing (or better, from the PDF itself), and a client-rendered thumbnail must never feed them. If the client path is used, the page menu says which renderer drew the page, as the session source already reports the server's (`renderer`).

### Privacy, hosting, and the console's build

- **Local-only jason-web (the server on the same machine):** the "files never leave the machine" benefit of a browser renderer does not exist; the bytes only go from disk to a process on the same machine. A browser renderer adds a bundle and a failure mode and removes nothing.
- **Hosted, multi-tenant portal ([tenancy.md](tenancy.md)):** the case for the client path. Rendering in the browser saves server CPU, cache disk (`split.thumbnail_cache_bytes`) and, if the file is read from the person's disk and never uploaded until apply, bandwidth and storage for drafts a person abandons. It also means the file is not on the portal until a person applies, which is a real privacy gain for a draft. But the splitter's draft, facts, suggestions and review all read the server's copy (section 0), so "never uploaded until applied" would mean the server could not suggest, flag or review. That is a different product: a **client-only editor** (marks only) with the apply uploading the file or just the ranges. It is described under open decisions, not recommended.
- **Third-party script hosting:** self-host every script, wasm, cmap and font file in the console's own build and serve from the console's origin; no CDN (the console's CSP and the repository's no-third-party rule). pdf.js's worker is loaded from a URL: serve it from the same origin.
- **CSP and XSS.** WebAssembly needs `script-src 'wasm-unsafe-eval'` (or the legacy `'unsafe-eval'`) in a browser enforcing a CSP; pdf.js also builds a worker from a blob in some modes and evaluates fonts through the browser. The server's existing headers set `Content-Security-Policy: sandbox` for the picture and file routes (`src/jason/web/split.py`, `app.py`); the console page's own policy is not part of what I read, so what `wasm-unsafe-eval` would loosen there is **unverified and must be checked before a go**. pdf.js has had script-execution advisories in its history (verify against the project's security page before pinning a version); a PDF is untrusted input that the client path would parse in the person's tab, where today it is parsed only on the server. The `isEvalSupported: false` option and a sandboxed iframe or worker for the viewer reduce that.
- **Licensing and bundled assets.** pdf.js: Apache-2.0; the package carries its own openjpeg and qcms licences in the `wasm` folder (`LICENSE_OPENJPEG`, `LICENSE_QCMS`, each shipped). Its cmaps and standard fonts are separate files with their own notices (check `cmaps/LICENSE` and `standard_fonts/LICENSE_*` in the package before shipping; **not read here**). mupdf.js: AGPL or commercial. pdf-lib: MIT (its repository has had no release since 2021; verify). tesseract.js: Apache-2.0 (the repository's page); its language data is a separate download (section 5).
- **Bundle size and the existing build.** The console is React 18 with Vite 6 (`ui/package.json`). pdf.js would be a dynamic `import()` behind the compare pane or the "client renderer" switch, never in the main chunk: about 1.4 MB over the wire for the library, worker and wasm, and a cmap and font set fetched on demand. `vite.lib.config.ts` suggests the console is also built as a library; the optional engine must stay out of that build (not read in full: unverified).
- **Jason's rules.** Nothing applies on jason's initiative: a client renderer changes nothing about apply. No file names in URLs: a client path must not put a name in a query string, a blob URL's name is opaque, and `File.name` is never sent except as the person's label. Facts have a source: a thumbnail's source is "drawn by pdf.js in your browser", shown. No invented numbers: no client-measured fact is shown as the file's measure.

### Recommendation

Keep the server renderer as the default and the only one that feeds facts. Add the browser renderer, if at all, as an **optional, lazy-loaded fallback** for (a) a deployment where `renderer_name()` is empty (the route answers 503 today), and (b) the compare pane at 1,600 px. Not the grid on a phone.

## 4. Per-page facts from pixels and the text layer

| Fact | In the browser | Verdict |
|---|---|---|
| Blank or marked | ink share from a 96 to 200 px canvas: 0.05 to 1.5 ms a page (measured loop), but drawing the page first costs 15 to 80 ms | the server already draws and measures once per file by hash; do not repeat. A browser value would differ from the server's by renderer (section 3) |
| Sideways (`turn`) | needs each text line's direction: `getTextContent()` in pdf.js has transforms, so it is possible (unmeasured) | the server's `turn` is read from the PDF's text layer carried through `/Rotate`; leave it there. "A scan with no text layer is never called sideways" must not be loosened by a pixel guess |
| Page-number run ("2 of 7") | text layer via `getTextContent()` | possible, no gain: the server's `PageFact.label` exists and feeds the cue table |
| Near-duplicate images | a perceptual hash from a canvas | differs from `phash` (the server's mean-hash of its 16 by 16 picture); two hashes of the same page from two renderers would not compare. Server only |
| DPI, colour, codec, size change | need the image dictionaries and the page box, not the pixels (the browser would draw to find them, which is the wrong order) | server (`pdf_preflight`'s readers) |
| Orientation of a scan | needs a layout model or OCR | not worth a client model |

**The principle.** The splitter's facts are measured from the PDF by the server, stored by hash, and every suggestion carries them as its source (pdf-splitter.md 2). A client-measured fact would be a second, untrusted source for the same field. If a client fact is ever sent, it goes in a separate field (`clientHint`), is never read by `split_suggest`, `split_flags` or the apply, and is shown with its source, or it is dropped.

## 5. OCR in the browser

- **tesseract.js** (Apache-2.0 per the repository's page): WebAssembly port of Tesseract, in a worker; v5 made language files smaller (the project says 54 percent smaller for English). The wasm core and the language data are separate downloads; both can be self-hosted (the project documents local installation; the option names `workerPath`, `corePath`, `langPath` are from memory: **verify**). Speed and accuracy on 200 dpi bilevel archival scans: **not measured**.
- **ONNX / RapidOCR in WebAssembly:** the server's own engine for OCR of a library part is Docling with RapidOCR (pdf-splitter.md 9.5); a browser build exists in the ecosystem (onnxruntime-web with the detection and recognition models, several tens of MB). **Unverified, not run.**
- **Why it is the weakest candidate.** OCR is the one step that would be worth offloading for cost, and the one where a result is a *reading* the library keeps (text for search and for quoting; "Do not invent CC&R quotes ... quote document body text only when you have the file", AGENTS.md). A browser-OCR text layer would be an unchecked reading entering the library. If ever done: client OCR is a hint to display, the server keeps its own reading, and a text produced client-side is never stored as the file's text.
- Verdict: **no go.** Keep OCR on the local lane. Revisit only for a hosted portal without a GPU or CPU lane, after a measured accuracy comparison against the server's engine on the same made-up and real scans.

## 6. Cutting in the browser versus uploading page ranges

| Option | What happens | Verdict |
|---|---|---|
| **Server cut from the server's copy** (today) | `pypdf`, deterministic bytes; hash, collision and duplicate rules on the exact output | keep. 137 ms to cut 11 of 2,000 pages including opening a 93 MB file |
| **pdf-lib in the browser** | measured 864 ms to load the 93 MB file (whole) and 12 ms to copy 11 pages and save; unmaintained since 2021 (verify); copies pages but not always outlines or form structure (unverified here) | a cut by a client is a file the server did not make: its bytes are not the ones `pypdf` writes, so determinism ("the same pages cut twice give identical bytes", 9.4) and the duplicate check differ |
| **pdf.js** | does not write PDFs | not a cutter |
| **qpdf in WebAssembly** (a few third-party builds) | faithful page selection, bigger wasm | not run; unverified; adds a second cutter |
| **Upload only the ranges** | the browser sends the pages a person marked rather than the whole file | only after marks are final, so it cannot support the draft, the suggestions or the flags, all of which read the whole file (section 0). It is useful in one case: a file above `upload.max_bytes` where a person already knows the ranges |

Verdict: **server cuts**. A client-side "send this range" is allowed only as a labelled partial source. The server's session source records `partial: true` and the page offset, and refuses suggestions that need the neighbouring pages, rather than quietly working from a fragment.

## 7. Hashing, dedupe, idempotence

- **SubtleCrypto SHA-256** is fast (71 ms for 105 MB here) and produced the same digest as Python. Limits: no incremental API (so a 400 MB file means a 400 MB buffer; for large files a chunked hash of fixed-size blocks, hashed together in a Merkle-style manifest, needs a pure-JS or wasm implementation, an added dependency: unverified), and it needs a secure context.
- **What it buys.** (1) *Skip an upload the server holds*: the client asks "do you have sha256 X for this community?" and, if yes, opens the existing session. (2) *Idempotence*: the same bytes resume the same draft, which pdf-splitter.md section 1 already says; the client hash makes it free of an upload. (3) *Dedupe*: parts are hashed by the server at apply, as now.
- **Privacy of the query.** "Do you hold this hash?" tells a caller whether a file is held. In a multi-tenant portal the answer is per community and per signed-in person's access, never global (a global answer is a side channel for "does anyone hold this document"); a confidential file's presence is an answer only to someone who may see it. The hash goes in a request body, never in a URL, as with names (AGENTS.md and [console/security-and-privacy.md](console/security-and-privacy.md)).
- **Trust.** The server hashes what it receives and keys its copy by that digest. A client that lies about its hash gets, at worst, a refusal or its own upload; a client must never be able to claim another file's pictures by sending that file's hash (the "have it" answer must return a session only the caller may open).

## 8. Upload strategies

Today: base64 in one JSON request, bounded by `upload.max_bytes` (default 100 MB). Base64 inflates by a third and holds the string in the browser and the server at once.

| Strategy | Benefit | Cost and risk |
|---|---|---|
| Raw `multipart` or binary body instead of base64 | 25 percent fewer bytes; no string copy | one route change; no new state |
| **Chunked and resumable** (fixed 4 to 8 MB parts, a manifest, the server assembles and hashes) | a flaky connection or a phone resumes; a file above the web server's request ceiling can move | new server state (partial uploads), a sweep for abandoned ones, quota accounting under `split.thumbnail_cache_bytes`-style bounds; the assembled file is hashed and checked as a whole |
| **Skip by hash** | no upload for a file the server holds | section 7's access rule |
| **Client-side preflight** | a refusal before the bytes move: size, header, encrypted, page count against `split.max_pages` | advisory only; the server's words win |
| Range upload (section 6) | for a file too large to send whole | a partial source; the server must say so |

None of these lets the client decide anything the server applies. Each ends with the server holding bytes it hashed itself, in the copy the splitter already keeps.

## 9. Recommended hybrid

1. **Default (no change).** Server renders; the browser shows plain images; the server measures and holds every fact; the server cuts; the browser only marks. The file is in the server's copy keyed by its own SHA-256.
2. **Phase A, client conveniences.** SHA-256 in the browser, skip-by-hash, a raw or chunked upload, a client preflight. No library beyond SubtleCrypto. All advisory.
3. **Phase B, an optional client renderer** for (a) no server renderer, (b) the compare pane at high zoom, (c) a hosted portal that chooses it for cost. pdf.js, self-hosted, lazy-loaded, with its wasm, cmaps and fonts, behind a flag, with a startup self-test for JPEG 2000 and CCITT.
4. **Never client-side:** facts that suggestions, flags or apply read; the cut that apply writes; text from OCR stored as the file's text.
5. **The server is the authority.** Every client value is re-measurable or advisory. A client claim that the server cannot re-derive is dropped.

## 10. Phased plan with go and no-go tests

| Phase | Work | Go when | No-go when |
|---|---|---|---|
| A1 | Client SHA-256 and "do you hold this" | the digest equals the server's for the 105 MB test file and for a 0-byte, 1-byte and exactly-chunk-size file; a stranger's session id or hash returns nothing it may not see | a different digest in any browser tested; any answer that reveals another community's holdings |
| A2 | Raw or chunked upload | a 100 MB file uploads and resumes after a dropped connection; the server's hash equals the client's; abandoned parts are swept | partial uploads count against no bound, or a half-uploaded file can be opened |
| A3 | Client preflight | every client refusal is reproduced by the server with the same words | a client accepts what the server refuses and the person is not told |
| B1 | pdf.js behind a flag, one page at a time | the self-test draws a known JPEG 2000 and CCITT page non-blank; 30 pages at 200 px complete at 20 pages a second or better on the target phone class; peak tab memory under the console's 20 MB phone budget for decoded pictures (pdf-splitter.md 5.9) plus the file buffer | a silent blank page for any codec; a long task over 100 ms in a scroll; the console's CSP loosened beyond `wasm-unsafe-eval` |
| B2 | Real JBIG2 and mixed scans | a set of real JBIG2 and CCITT pages (private, counts only in a report) matches the server's drawing within the 4 to 7 level margin measured here and never draws blank | any page where only one renderer shows content |
| B3 | A hosted portal's choice of renderer | server CPU and cache disk per community drop by the measured amount | the cost saved is smaller than the support cost of two renderers |
| C | Client OCR | accuracy within a stated margin of the server's engine on a gold set; hint only | text stored as the file's text without the server's own reading |

## 11. New limits and settings (through `jason.limits`)

None is registered; each needs a row with its `why` and `when_hit` words as [instance-limits.md](instance-limits.md) requires.

| Key | Kind | Proposed default | Notes |
|---|---|---|---|
| `upload.chunk_bytes` | size | 4 MB (1 MB to 32 MB) | the part size of a resumable upload; the maximum is bounded by the web server's own ceiling |
| `upload.partial_days` | time | 2 days (1 to 14) | how long an unfinished upload's parts are kept before the sweep removes them; a retention with a minimum |
| `upload.partial_bytes` | size | 1 GB (100 MB to 16 GB) | the space unfinished uploads may hold in all, per community |
| `split.client_render` | switch | off | allows the optional browser renderer; a convenience or cost switch, not a safety check. A community administrator turns it on; the operator may force it off |
| `split.client_render_max_pages` | count | 500 (50 to 3,000) | the largest file a client renderer is offered for, so a phone is not given a 2,000-page file |
| `upload.hash_skip` | switch | on | whether "do you hold this hash" is answered at all; off in a deployment that treats even that as a disclosure |

`upload.max_bytes`, `fetch.max_bytes` and `split.max_pages` keep their meaning and are still enforced by the server on what it receives, whatever the client says.

## 12. Open decisions for the user

1. **Is there a hosted multi-tenant portal on the road map?** The client renderer's case is almost entirely that. For a local jason-web it is not worth a bundle and a second renderer. Recommendation: build phase A (hash, skip, chunking) now, and defer phase B until a hosted deployment is real.
2. **Is a client-only editor in scope?** Marks in the browser, the file never uploaded until apply. It gives up suggestions, flags, and review, which read the whole file on the server. Recommendation: no.
3. **Which licence line for the client bundle?** pdf.js (Apache-2.0) is acceptable; mupdf.js (AGPL or a paid licence) is not recommended; pdfium-in-wasm is untested here. This is also decision 2 of [pdf-splitter.md](pdf-splitter.md) on the server, and the two should be settled together, with counsel for the AGPL reading.
4. **Is `wasm-unsafe-eval` acceptable in the console's CSP?** Needed for pdf.js's wasm (JPEG 2000) and any wasm engine. Check the console's current policy first (not read here).
5. **Should a "do you hold this hash" answer exist at all?** It is a disclosure of holdings, even when scoped to the caller's community (limit `upload.hash_skip`).
6. **Resumable upload state.** Accept new server state (partial parts, a sweep, quotas) for large files, or keep one request and raise the ceiling.
7. **A real JBIG2 corpus.** The measurement could not generate JBIG2. A private set, with counts only reported, is needed before any go on B2.
8. **Set the renderer for the server first.** pypdfium2 was not installed in this checkout's environment, so the server numbers above are PyMuPDF's; if pypdfium2 is chosen (decision 2), re-run `scripts/client_pdf_server_bench.py --engine pypdfium2`.

## 13. Reproducing the measurement

In a scratch folder outside the repository: `npm install pdfjs-dist@5.4.149 pdf-lib@1.17.1 playwright@1.63.0` (with `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1`, using the cached Chromium), then

```
python scripts/client_pdf_make.py SCRATCH/pdfs
node scripts/client_pdf_bench.mjs SCRATCH/pdfs SCRATCH/pics      # run from SCRATCH
PYTHONPATH=src python scripts/client_pdf_server_bench.py SCRATCH/pdfs --pictures SCRATCH/pics
```

All inputs are generated; no real archive is read. `scripts/client_pdf_make.py` writes CCITT, JPEG, Flate and JPEG 2000 image PDFs and a text PDF; it writes no JBIG2.

## What is unverified

The phone and Safari and Firefox behaviour; JBIG2 in either renderer; every figure for EmbedPDF, mupdf.js, CanvasKit, tesseract.js and ONNX OCR (taken from each project's own page or marked "from memory"); the console's CSP; pdf.js's advisory history; the licence text of its cmaps and fonts; pdf-lib's fidelity on outlines and forms; the caller's recorded server timings (about 2.1, 3.8 and 47.6 ms per page).
