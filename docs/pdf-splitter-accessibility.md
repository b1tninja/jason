# The PDF splitter: an accessibility audit

An audit of the splitter's screens against WCAG 2.2 level AA and the WAI-ARIA Authoring Practices, made on 2026-10-11 at commit `77623b4`. It reads the code, then runs the built console on made-up data and records what a browser and an automated checker report. The audit itself changed no code: every defect below has a file and a suggested fix, and the [test plan](#6-automated-test-plan) says how to keep each one fixed. **The fixes were then made** (2026-10-11, the commit that carries this update): the defects marked Fixed in section 4 are fixed and the conformance table in section 3 is re-run against them; what is still open is named in section 4 and in [section 7](#7-open-decisions). The tests are `e2e/tests/a11y.spec.ts`, `ui/src/views/splita11y.test.tsx`, and `ui/src/views/contrast.test.ts`; the table's "Evidence" now says what each one checks, and the first sentence of a changed row says what it was. The splitter's own accessibility notes are in [pdf-splitter.md](pdf-splitter.md) section 5.8; this document is the evidence for them and the list of what is left.

## 1. Scope and method

**Screens.** The start page (`#/setup/split`: the made-up-file link, the open panel with its three tabs, the library browser, the drafts table) and the editor (`#/setup/split/<id>`) in every state: the album, the filmstrip, the scroll view, the list; the toolbar menus; the segment strip; the segments, compare, and review drawers; the page menu; the flags dialog; the keyboard map; the tool panels; the selection bar; the magnifier; focus mode. The console's own header and navigation are outside this audit except where they change the splitter's result (tab order, page title, 400% zoom).

**Code read.** [PageGrid.tsx](../ui/src/views/PageGrid.tsx), [SplitEditor.tsx](../ui/src/views/SplitEditor.tsx), [SplitMenus.tsx](../ui/src/views/SplitMenus.tsx), [SplitDrawer.tsx](../ui/src/views/SplitDrawer.tsx), [SplitPanes.tsx](../ui/src/views/SplitPanes.tsx), [SplitFlags.tsx](../ui/src/views/SplitFlags.tsx), [SplitRail.tsx](../ui/src/views/SplitRail.tsx), [SplitReview.tsx](../ui/src/views/SplitReview.tsx), [SplitView.tsx](../ui/src/views/SplitView.tsx), [LibraryBrowser.tsx](../ui/src/views/LibraryBrowser.tsx), [Loupe.tsx](../ui/src/views/Loupe.tsx), [splitModel.ts](../ui/src/views/splitModel.ts) (the words a cell says), [split.css](../ui/src/views/split.css), and the colour tokens in [styles.css](../ui/src/styles.css).

**Browser runs.** The built console (`npm --prefix ui run build`) served by the end-to-end launcher ([e2e/serve_e2e.py](../e2e/serve_e2e.py), see [e2e/README.md](../e2e/README.md)) on a throwaway data folder with sign-in bypassed, driven by Playwright 1.63.0 in Chromium 1243 with axe-core 4.14.0 (rules tagged `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`, and `best-practice`). Everything used the made-up 120-page draft (`#/setup/split/demo`) and a 3000-page one (`?pages=3000`) for the window; the library tab read the launcher's three made-up files. Each state got an axe run and an accessibility-tree snapshot (`ariaSnapshot`). Screenshots were taken at 390, 768, and 1440 px, at a 320 by 256 px viewport (400% zoom of a 1280 by 1024 window), at 640 by 512 (200%), with forced colours on, in the dark scheme, and with reduced motion. The scripts are scratch files and are not part of the repository; the [test plan](#6-automated-test-plan) turns them into tests.

**States used in the table.** *Pass*: checked and met. *Partial*: met in some states or by some controls, with the gap named. *Fail*: not met, reproduced. *Unverified*: needs a screen reader or a device this audit did not have.

## 2. What is already right

These are design decisions to keep, and the tests in section 6 protect them.

- **One tab stop for the pages.** The grid has a roving tab index: one button in it has `tabindex="0"`, and the grid itself is the stop when the focused page has been unmounted. Arrow keys, Home, End, Page Up and Page Down move by page and by row (rows with bands included). Marking is Enter or Space on a native button, so it is a real click that carries Shift.
- **Marking, range select, and undo have complete keyboard paths**: Enter or Space marks, Shift and the arrows extend a selection (announced in a status line, `aria-selected` on each cell), Shift and Enter selects a range, `Z` and `Y` undo and redo, `L` opens the page menu, `N` and `P` walk the starts, and the Pages menu has "Menu for page N" so a touch user without a long press has a way in.
- **The pictures are decorative and the cell speaks for them.** Each page picture has `alt=""`; the cell's button carries the name (page number, measured state, first line when the text layer gave one, and what the page is in the draft). A confidential file's name is the page number alone.
- **Menus follow the menu button pattern.** Toolbar with one tab stop, `aria-haspopup`, `aria-expanded`, `menuitemcheckbox` and `menuitemradio` with `aria-checked`, type-ahead, Left and Right to the next menu, Escape returning focus to the button. A chosen item is a tick and a word.
- **State is never colour alone.** A start is a left border and the words "Start 3"; a suggestion is a dashed border and "Suggested, High"; a selection is a tint and a ring plus the status line; flags are a glyph and words; confidence is a word and dots.
- **Drawers return focus.** The segments and compare drawers move focus in when they open and back to what opened them when they close (checked by key and by control). The tool panel returns focus to the menu button that opened it.
- **Motion respects the preference.** The drawer slides, the scrim fade, the picture fade, and the lens fade are all inside `prefers-reduced-motion: no-preference` (computed `animation-name: none` and `transition-duration: 0s` when reduced).
- **Dark mode has no contrast failure** in the album or the compare drawer (axe, dark scheme; the other states were scanned in the light scheme only).
- **No sideways page scroll** at 390, 768, 1440, 640 by 512, or 320 by 256.
- **No drag-only drawer.** The edge tabs and grips are buttons; the drag is an extra.
- **The library browser is plain HTML**: a labelled search, `aria-pressed` filter chips with counts, a real table with `th scope`, a radio and its label for choosing a file, and a status line that reports the count (zero axe violations on the start page, one on the library tab).

## 7. Open decisions

1. **How much of a page's text is exposed, and how.** Today a cell says its number, measured state, and first line (from the text layer, or the server's reading); a confidential file says only the number. The first line is a title guess, not a transcription. Options: (a) keep it; (b) add a "Page text" region to the compare drawer, filled from the stored text layer or the stored OCR reading, with the caveat that a machine reading can be wrong, held back for a confidential file; (c) nothing more. The recommended answer is (b), because comparing pages is the job a sighted person does by looking, and a person who cannot look has no other way to tell a cover sheet from a first page. It needs the store to return a text reading per page (a new, bounded read), and a rule for pages with no text layer ("no text layer: the picture cannot be read here").
2. **Cell name format.** *Settled in the fixes, for the board to confirm:* the name is the visible words in the order they are drawn ("Page 7, Start 2, Blank, S2"), the keys are said once for the grid, and the first line and the segment are the description. Speech control (2.5.3) outranked brevity; the name is short anyway (the longest is under 60 characters).
3. **Grid, or something else.** The album is a `grid` whose cells are one button each, which is the pattern for a two-dimensional set of widgets. A `listbox` of `option`s cannot be two-dimensional, and a table of toggle buttons loses arrow-key movement. Keep the grid; the open question is whether the roving focus should land on the `gridcell` (the APG's preferred target) rather than the button inside it.
4. **Dialog modality.** *Settled in the fixes:* modal. The three dialogs trap Tab, bring stray focus back, and close on Esc from anywhere. The background is not made `inert`; the focus guard does the work.
5. **Single-key shortcuts.** Default on, with a switch (D15), or default off with a first-run prompt. The editor's speed depends on them; a switch meets 2.1.4 either way.
6. **Magnifier default for hover devices.** On by default for a mouse or trackpad (today). It is user-controlled, but a lens that appears under the pointer on every page is the most likely thing to annoy a low-vision user who is already zoomed in, and it is not hoverable. Options: keep it on, make it off until chosen, or off when the page is zoomed past 200%. The recommended answer is off when the browser zoom is above 200%.
7. **Pointer targets: 24 or 44.** The code uses 44 px on coarse pointers and 24 or less elsewhere. WCAG needs 24; the proposal is to keep that and fix only the controls under it (D18).
8. **What the start page offers for help (D19).** A link to the keyboard map is cheap; whether it also links the document is the board's decision about how public the instructions are.
9. **Announcements policy.** *Settled in the fixes, for the board to confirm:* one message region for acts and an alert for faults; the save state (and its time) is on the screen and is never spoken. Whether "Draft saved" should ever be spoken (a reassurance some users want) is still the open part.
10. **A dev dependency for tests.** *Settled:* `axe-core` in `e2e/` only, injected into the page; `@axe-core/playwright` was not needed.

## 8. What this audit could not verify

- **Screen readers.** No NVDA, JAWS, VoiceOver, or TalkBack was run. Every "what it announces" claim is read from the accessibility tree and the live-region log, and the scripts in section 5 are how to check them. The grid's behaviour in NVDA's focus mode and VoiceOver's interaction model, and how each queues three polite messages, are the likeliest places for a surprise.
- **Touch.** The long press, the lens dragged above a finger, and the drawer drag were read in code and screenshotted at phone size in an emulated touch context; they were not used on a device.
- **Real scans.** The pictures and names came from the made-up draft. A real file's first-line reading, its sideways flags, and its blank-page words are generated the same way, but their length and content vary.
- **Escape during a start drag** (2.5.2) and the **slider thumb's** size and contrast were not measured in a browser.
- **Windows high contrast** was emulated with Chromium's forced-colours media feature, which is close to but not the same as a theme such as Aquatic.
- **The console** (header, navigation, sign-in, the scratchpad) was only looked at where it changed the splitter's result. Its own audit is a separate piece of work; D7 and D8 start there (a title and a skip link on the splitter's screens only).
- **After the fixes:** no screen reader was run on them either. A real Tab from a fresh load of a draft reached the skip link in the console's browser pane, while headless Chromium in the test suite started its Tab order below it (unexplained; the test reads the tab order from the page). The console header is taller than a 256 px window, so at 400% zoom the pages begin below the fold.
